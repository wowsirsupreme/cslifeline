# Machine-learning methodology

## 1. Question the model answers

"Will this learner's assessment accuracy over the next four weeks fall below 50 %?" — asked at a cut-off date, using only what has been recorded before it. The output is an **early-warning indicator** with a probability, a category, the main contributing factors and a suggested action. It is not a diagnosis or a judgement of ability, it is never shown to students, and every prediction stores its model version, feature version, date and features.

## 2. What was wrong in v3 (and is fixed)

| v3 problem | v4 approach |
|---|---|
| Label computed from the same features (`at_risk` = low accuracy / many misconceptions / tab switches) — the model rediscovered its own rule (target leakage). | Label is a **future** outcome (next 28 days); features stop at the cut-off. Tested in `ml/tests/test_pipeline.py`. |
| Scaler fitted on all rows before cross-validation. | All preprocessing inside an sklearn `Pipeline`, fitted on training folds only. |
| Row-level stratified K-fold, no time order. | Learner-grouped 5-fold CV on the training term; a single final test on a **later term with different learners**. |
| Tab switches up-weighted ("BW-RF"). | Page interruptions are recorded as context only and are not features. |
| No model version or approval; predictions written straight to production. | Model registry, candidate → production promotion by an administrator with a recorded reason; rollback; predictions labelled `validated` or `demonstration`. |
| Session completion read from final status. | Completion counts a session only if it ended before the cut-off (feature version fv-1.1). |

## 3. Data

* **Development data (now):** synthetic cohorts generated by `scripts/synthetic/generate.mjs` — H1 (Sep–Dec 2025, 302 learners) for training, H2 (Jan–Apr 2026, 282 different learners) as temporal hold-out, C (current term, 92 learners) for demonstration predictions. Answers are generated from an item-response model with held misconceptions and marked by the application's own marking engine, so the records are exactly what the app stores. Synthetic results test the pipeline only.
* **Study data (later):** the teacher portal's research export (pseudonymous; by default only learners with recorded consent). Add a `cohort` column per term and run `python -m cslifeline_ml train --data <folder> --train-cohort <earlier> --test-cohort <later> --real`.

Synthetic and real data are never mixed: `load_synthetic` refuses any row without `is_synthetic = true`, registry entries record `trained_on`, and synthetic-trained models can only be promoted as demonstrations.

## 4. Features

Fourteen features from performance, misconception evidence, engagement and behaviour (DATA_DICTIONARY.md §4). Identity attributes (names, gender, school fees, ethnicity…) are not collected and not used. The browser (`risk.js`) and Python (`features.py`) implementations are tested for exact equality on real synthetic learners (`ml/tests/test_parity.py`), and the browser's logistic inference is tested against scikit-learn's to 1e-9.

## 5. Models compared

Interpretable baselines first, then more complex models, all with mean imputation inside the pipeline:

| Model | Settings |
|---|---|
| Logistic regression | standardised features, C = 1 |
| Decision tree | depth ≤ 4, ≥ 20 learners per leaf |
| Random forest | 300 trees, ≥ 5 per leaf |
| Gradient boosting | 200 trees, depth 3, learning rate 0.05, subsample 0.8 |
| XGBoost | 300 trees, depth 3, learning rate 0.05 (if installed) |
| Support vector machine | RBF kernel, Platt-calibrated |

**Selection rule:** the most interpretable model whose cross-validated PR-AUC is within 0.02 of the best. PR-AUC is used because at-risk learners are a minority and the cost that matters is finding them.

**Sequential models (LSTM) are not used.** Each learner contributes two prediction points per term and a few hundred responses; this is too little longitudinal data to train a sequence model without overfitting, and it would be harder to explain to teachers. The trend features capture change over time. The question should be revisited only with several terms of real data.

## 6. Thresholds

Chosen on the training term's out-of-fold predictions, then frozen before the hold-out test:
* **moderate** (flag): the highest threshold that keeps recall ≥ 80 % — an early-warning tool should rarely miss a learner who needs help;
* **high**: the lowest threshold with precision ≥ 70 %; if that is not reachable, the F1-maximising threshold above moderate (the rule actually used is recorded in the registry entry).
Administrators can set fallback thresholds in Settings; a registered model's own thresholds take precedence.

## 7. Evaluation

Accuracy, precision, recall, F1 (at both thresholds), ROC-AUC, PR-AUC (with the prevalence baseline), confusion matrices, Brier score and expected calibration error with a reliability table, prevalence (class imbalance), subgroup performance by school and grade, an analysis of false negatives versus true positives, an ablation (outcome features only vs. full set) and a cross-platform comparison (CS Lifeline only / WOW Sir only / DBWOW only / combined), each with a learner-level paired bootstrap 95 % confidence interval. A gain is reported only when its interval excludes zero.

## 8. Explanations

For logistic regression, each feature's contribution is its exact term in the log-odds. For other models, the contribution is the change in predicted risk when that feature is set to the training mean (occlusion). Teachers see the factors that raise risk, phrased in plain language (`describeFactor`), and a suggested action that also uses the learner's misconception findings.

## 9. Controlled improvement

1. New eligible data arrives (research export, or integration events with verified links).
2. `python -m cslifeline_ml train` validates (synthetic/real separation, labels), rebuilds features, trains and compares all models, writes a report and registers a **candidate** with data hash, seed and library versions.
3. The report is compared with the current production model; the registry keeps every version.
4. An administrator promotes a candidate with a reason (or restores an archived model — rollback). A synthetic-trained model can only be a demonstration.
5. Predictions are generated in Python and imported, or computed in the browser for logistic models.
Nothing is retrained or promoted automatically.

## 10. Misconception engine (rule-based, evaluated separately)

Misconceptions are classified by rules over repeated evidence (engine mce-1.1, `engine/misconception.js`): never from one wrong answer; distractor choices count as diagnostic only if the question also has wrong options not linked to that misconception; and errors must exceed the learner's own error rate on other questions by 25 points to be "demonstrated" (15 for "possible"), otherwise they are reported as a knowledge gap. The margins were tuned on synthetic cohort H1 and evaluated on H2 against the simulation's ground truth (`scripts/evaluate-misconceptions.mjs`; results in MODEL_EVALUATION.md §5). Teacher reviews are stored as separate, teacher-validated labels and can later be used to evaluate or train a supervised misconception model.

## 11. Reproduce

```
node scripts/synthetic/generate.mjs --seed 2026
cd ml && python -m cslifeline_ml train
python -m cslifeline_ml promote <version> --reason "…"
python -m cslifeline_ml predict --model <version>
cd .. && node scripts/attach-ml-to-demo.mjs && node scripts/make-feature-fixture.mjs
node scripts/evaluate-misconceptions.mjs H2
```
or run `ml/notebooks/CSLifeline_Research_Pipeline.ipynb` in Google Colab.
